## P0 — acceptance and evidence integrity

### 1. Attestation identifies the source revision, not the audited README

**Confirmed code-contract gap; occurrence against a real accepted replacement not established.** `scripts/run_acceptance_writer.py:362` emits each record with repository, lane and upstream revision but no audited candidate/README digest or seal identity. `ops/checks/portfolio_delivery_count.py:589` reads accepted records into a `(repository, lane) -> revision` mapping; `apply_attested` at approximately line 657 accepts a current recertified outcome when that source revision matches. `scripts/run_m9_seeder.py:91` also uses same-revision judgement when selecting clean controls. A targeted repair or a new seal with different README bytes at the same source SHA can therefore inherit an audit of different content. Attesting the writer does not bind the content that the auditor saw.

**Fix direction:** bind clean controls, audit input, writer record and counter to a cryptographic digest of the actual audited candidate bytes and appropriate source/dependency identity. Verify that identity after current-code rendering and re-certification, before counting or publication. Preserve all old seals and their provenance (R10); re-audit only changed audited scope, not a global regeneration. Do not label every existing candidate defective merely because the binding is absent.

**Falsifier:** two differently rendered README/seal outputs from the same repo, lane and upstream revision: an attestation for the first must not accept or suppress audit of the second. Also test replay of identical bytes, mismatched digest, missing/malformed digest, historical records, stale/missing artifacts, and signed-but-wrong candidate. Verify the whole seeder → frozen findings → writer → counter → publication chain, not only a pure helper.

### 2. Mandatory canaries and cited evidence are not established

**Confirmed current implementation / BL-024.** The writer emits `canaries: {}` (`scripts/run_acceptance_writer.py:370`) and reports `citations_checked: structural` (`scripts/run_acceptance_writer.py:281`). `src/repo_presenter/acceptance/record.py:285` treats `all({}.values())` as true. The adopted delivery contract §5.2–5.3 requires applicable per-candidate canaries to be caught and requires re-checkable evidence; §7 budgets canaries for approximately one in five candidates. Selection and applicability need to be traced: an empty map alone cannot establish whether a required selected canary ran. Therefore the automated count is a real attested system output but does **not** establish that those stronger checks ran or that cited source lines are valid. This is an absence of demonstrated assurance, not a finding that every counted candidate is wrong.

**Fix direction:** first trace which canaries apply, how they are seeded without leaking, and the intended nonempty semantics; check cited paths, line ranges, content and pinned source/revision using independent evidence. Make missing, malformed, failed and mismatched evidence fail closed where required. Measure existing records and no-regression impact, and do not fabricate canaries or source checks. Negative controls must distinguish an actually caught canary from an empty map and a plausible-looking citation from wrong file/line/revision.

**Further coverage question:** the writer supplies one `recertify` verdict (`scripts/run_acceptance_writer.py:370`), while `AcceptanceRecord` accepts any nonempty all-true mechanism-verdict mapping (`src/repo_presenter/acceptance/record.py:278–297`). Trace whether recertification actually covers every applicable certified responsibility class; the aggregate label alone does not prove it. Remove one required class in a negative control and ensure acceptance fails. This is an unproved coverage concern, not a demonstrated missed defect.
