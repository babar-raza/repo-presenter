The decisive risks are not just low throughput: (1) the acceptance record is not bound to the audited README bytes; (2) mandated canary and evidence checks are not proved by the current writer; (3) the factual reviewer can miss renderer-produced statements and shares incomplete facts with authoring; (4) repair and preservation can block or lose valuable content; (5) the autonomous loop is stopped and its green schedules may perform no production. These are different failure modes and require separate falsifiers.

**Deeper production assessment (second pass):** the recurring problem is a broken chain of identity and responsibility across otherwise useful stages. A candidate can be generated from one set of observations, repaired under a request key representing another state, re-rendered under newer rules, and finally counted using an audit linked only to source revision. Meanwhile, generator, deterministic checks and reviewer can all depend on the same incomplete facts. These mechanisms can create both false confidence and repeated rejection. They are design-level explanations supported to different degrees by the evidence below; no one defect is claimed to explain every failed run.

**Recommendation:** strengthen the contracts and transactions between the existing components, rather than build a replacement platform or treat a new prompt as the remedy. The target is not guaranteed byte-identical fresh model output: it is reproducible replay of the same evidence, controlled input drift, independently defensible content, repairs that converge or stop with a specific diagnosis, and measurable quality on repeated fresh runs. The detailed target and migration below are a design proposal, not a claim that the current implementation satisfies it. R27's architecture freeze and R38 still apply: implement evidenced needs in existing components; any expansion outside their smallest viable scope needs its own explicit justification.

**Architecture freeze — implementation boundary (owner clarification):** This review does **not** authorize a new architecture, infrastructure, module, framework, service, pipeline, generic provenance platform or broad programme of new mechanisms. R27 prohibits new mechanisms, stages, workflows, checks and record types unless a specific failing behavior cannot be fixed inside an existing component; then only the smallest necessary change is permitted and must be explained in its PR. The sanctioned exceptions in later owner rulings remain limited to their stated scopes. The target-design sections below describe desired properties and possible approaches, not a mandate to build every described structure or an implementation plan that overrides R27.

In particular, a universal byte-range provenance graph, a new immutable object store, a general transaction framework or a new orchestration system would exceed this boundary if built as infrastructure for its own sake. For each finding: first reproduce the concrete failure; inspect the existing data, bundle manifest, call store, repair ledger, checks and hosted pipeline; choose the smallest change to those existing components that resolves that failure; run its falsifier and portfolio non-regression checks; and verify that it improves a candidate or removes a named blocker. Add a field or a narrowly scoped existing-component change only if needed for the demonstrated case. If an existing component cannot provide a required outcome without a new mechanism or module, document the specific necessity and apply R27's smallest-change exception, rather than silently starting a platform project. Do not sequence all proposed identity, lineage and snapshot capabilities as prerequisites to producing candidates; solve the demonstrated highest-impact blockers while other eligible work proceeds under the existing gates.

**Practical examples:** the same-revision/different-README acceptance gap calls first for identifying and verifying the existing candidate digest in the existing audit/counter records, not a new evidence service. A cache-key alias calls first for full-hash validation in the existing call store, not a replacement cache platform. A repair that is written under the wrong key calls first for correcting and testing that existing repair route. The broader end-state discussion is useful to test whether those fixes interact safely; it is not permission to implement the entire end state.

**Fix direction:** bind clean controls, audit input, writer record and counter to a cryptographic digest of the actual audited candidate bytes and appropriate source/dependency identity. These mechanisms interact: an incomplete snapshot can change a prompt or claim; a model generates a plausible but unsupported sentence; a new check detects one form but the repair owner cannot mutate the printed source; a partial restore changes the planned input; the cache may return an older or repaired response under the same request identity; the subsequent rerender can differ from the bytes audited. Repeated runs may therefore explore different states, not repeat a controlled experiment. This interaction is a **causal hypothesis** supported by the individual code paths and historical cases; no single end-to-end trace proves every link. The first implementation task is to construct such traces from real artifacts, not to claim the hypothesis is already a measured root cause for every repository.

## Target properties and candidate approaches within the freeze

Read every proposal in this section under the implementation boundary above. None independently authorizes a new module, stage, workflow, record type or general infrastructure. Where a proposed property is broader than an evidenced failure, treat it as a test or future design consideration, not queued implementation.

### Preserve what already protects the project

Keep the existing two separately observable lanes, pinned source clones, fact polarity and direct execution, evidence-backed inherited-content dispositions, R14 item-level decisions, R9 internal-only provenance, independent reviewer and calibration controls, durable bundle refs/manifests, budget reservation and R43 rolling stop, effect-specific GitHub write gates, leases/run requests and taskcard/receipt process. `bundle_store` already verifies bundle manifests; `run_job` revalidates retrieved output against current facts/checks; retain and test those protections. R10 means existing seals remain durable, current checks apply to all, re-certification is zero-call where possible, and a version bump is not grounds to regenerate or destroy a seal. Do not replace functioning machinery merely to implement the proposal.

### A. Snapshot and run identity: separate absence from uncertainty

Extend the existing preflight, fact capture and bundle dependency records so one run references a **closed input snapshot**: repository and README commit/blob IDs, exact consumed source-file/content digests, ecosystem/toolchain versions, registry/manifest versions, relevant published-reference policy and its provenance, applicable prompt/model route and checks, and external-observation IDs with observation time, result, origin and expiry. Distinguish source truth from an HTTP observation, `UNKNOWN` from `CONTRADICTED`, and verified absence from an unreadable source. Retain the exact bytes or immutable content-addressed references needed to replay a decision; a refetched live URL is not replay evidence. At publication, independently refresh the applicable volatile sources and consumed upstream scope; if unavailable or stale, hold the effect, not fabricate a result.

Use typed states such as `NO_PRIOR_SEAL` (authoritative lookup confirmed absent), `SEAL_RESTORED`, `RESTORE_RETRYABLE`, `CORRUPT_EVIDENCE`, `RELEVANT_INPUT_CHANGED`, `IRRELEVANT_INPUT_CHANGED`, and `MECHANISM_CHANGED` within the existing preflight outcome. A remote timeout, permissions error, missing artifact, bad checksum or recertification exception must not silently become `NO_PRIOR_SEAL` and trigger a fresh generation. Resume after restoring/repairing state; when a consumed input actually changes, identify the affected stages and keep the prior seal. A full source HEAD change is a signal to evaluate relevance, not by itself evidence that every candidate must be regenerated.

### B. Replay and repair identity: immutable outputs, explicit lineage

Evolve the existing call store and repair ledger, not a second state service. For each stage output, record the **full** request hash, full output digest, canonicalization/version, exact consumed input/observation digests, producer and model identity, validation version and attempt ID. Retain raw provider response separately from normalized accepted output and repair output. Treat a repair as a new immutable revision with `parent_output_digest`, defect/finding IDs, changed units and evidence; update the active pointer only after rerender and validation. Never replace the original provider response under the original request identity. A cache is an accelerator; durable bundle/ledger references plus validated hashes are authoritative. Missing or mismatched hashes are a cache miss or retryable integrity failure, never a reason to trust an unrelated object.

`CallStore`'s short filename may be retained only as an index if the complete hash and object checksum are validated inside the record and collision handling is explicit. Use a full digest or a collision-safe bucket; JSON decode failure must be surfaced safely. Carry forward an explicit migration reader for existing cache artifacts. Do not bulk rewrite, delete or regenerate historical seals. A new graph may need more storage and a one-time evidence-inventory pass; use deduplication and retention policies that preserve referenced audit and seal evidence.

The stage transaction should prepare complete artifacts in the existing run/bundle directory, validate schema, lineage, content digests, owner scopes and current checks, then atomically promote a manifest/pointer with compare-and-swap or the existing transactional ref mechanism. A process killed between file writes must not expose a mixed-round candidate as completed. `cascade.py:422–505` writes local artifacts sequentially, but this alone does **not** prove a corrupt seal can be published: test the actual staging and `bundle_store` promotion path before deciding what must change. The transaction needs one owner per `(repository, lane)`, idempotent retry and auditable conflict resolution; retain immutable prior results on crash or lost race. Raw prompts, source excerpts and provider outputs can contain private data: define least-privilege access, redaction where compatible with reproducibility, encryption/retention and deletion policy before expanding artifact retention; never move private aspose.org material into public README output or expose seed secrets.

**Falsifiers:** force two request hashes with the same filename prefix; corrupt/missing payload and wrong full digest; retry original after one or multiple repairs; change one fact used outside the rendered prompt; compare fresh and restored cache states; concurrent workers write different candidates; kill after each stage write and during promotion; replay from a different machine with caches absent. A successful repair must reappear in the next recomposed README and must never alter a different request's historical result.

### C. Evidence and rendered-content ownership: remove the shared blind spot

Expand the existing facts/probes and README traceability so every consequential final rendered claim, example, table row, command and retained item can be mapped to its printed byte range, its producing stage/unit/renderer, source evidence and an applicable verification method. Coverage is measured over the **final immutable rendered README**, including deterministic templates and restored content, not only model-authored units or citations supplied by the author. A citation to a SUPPORTED ID is necessary evidence provenance, not proof that the sentence logically follows from it.

For generated claims, an independent checker should test the actual predicate against pinned source, public surface, manifest/registry or executable evidence as appropriate; use a separately implemented probe or independent source inspection where the author and deterministic checks share a fact extractor. Record scope, toolchain, evidence digest, polarity and unresolved reason. Do not turn probe disagreement, failed network or incomplete extraction into contradiction. A generated claim whose support cannot be established must fail closed or be safely omitted with the correct preservation decision. Valuable unchanged maintainer material is open-world: retain uncontradicted unknown text, track its status internally under R9, and do not manufacture public attribution or mark it verified. Source contradiction or a demonstrated unsafe example still needs an evidenced, proportionate action. This distinction also resolves the apparent tension between BL-008's broad wording and R9's explicitly permitted retained unverified examples: report the verification coverage and policy exception, do not claim all such examples executed.

For preservation, build on the current unit/disposition and findings register: all live headings, prose, lists, tables, diagrams and examples become obligations with `must carry`, `may remove with evidence`, or `undecided`; decisions cite source and rendered placement. Supply known prohibitions and retention obligations **before** authoring and reconciliation, not only as BC-18/BC-17 rejection after rendering. A single canonical printed-form transformation must be used by composer, checker, reviewer and parity accounting, with independent source validation of the resulting claim. If the implementation cannot identify which of two examples is refuted, preserve neither as a falsely verified generated example nor silently remove both; hold or make a targeted evidenced decision. Distinguish copied aspose.org output from an independent factual oracle: the live output is the quality floor (R2/R42), but a false upstream claim is not automatically true.

**Falsifiers:** a supported symbol name used in a false behavior sentence; two same-named symbols in different owners; renderer-only unsupported commercial claim; source-true fact omitted by extractor; transient registry failure; two example fences with only one contradicted; must-carry table member moved or rewritten; a claimed supersession whose replacement is absent; preserved unverified maintainer text with no public provenance. ### D. Repair as an owned, convergent transaction

Give every blocking finding a typed key: candidate digest and rendered span, finding class, independent evidence, responsible stage/unit/renderer/fact, acceptable change scope, and all validators that must be rerun. A monotone reduction of the known blocking set is a useful guard, but never proof of truth. An unattributable or ambiguous owner is a first-class diagnosis and route to repair the producer/facts; it is not a license to mark a reject resolved.

Unify the partial-restore/repair/recompose identity: the defect must name the bytes it inspected, and the patch must be applied to exactly the parent output whose downstream rerender consumes it. Require a stale-parent failure if another action changed that object. Measure repeated signatures and stop/reschedule systemic diagnosis rather than resetting the retry counter or alternating fixes. Batch only independent units whose writes cannot overlap. Check the final post-restore candidate again; temporary fixes are not the deliverable. Bound cost and rounds, while preserving all previous attempt artifacts for diagnosis.

**Falsifiers:** restore plus an unrelated BC failure; repair keyed to pre-restore vs post-restore parent; a repair that only changes ledger wording; a change that fixes BC-18 but causes BC-05 loss; duplicate/ambiguous finding quote; renderer-owned defect with no stage owner; repeated A→B→A; child process death before/after commit; two simultaneous repairs on same unit. **Release sequence for each demonstrated blocker:** (1) reproduce it offline using archived artifacts; (2) make the smallest fix in the existing component, with compatibility handling only where that failure requires it; (3) run its negative control and appropriate portfolio no-regression checks, pairing any new blocking rule with the producer fix; (4) run hosted CI and applicable zero-call R41 recertification, preserving seals; (5) after verified fixes and honest cost accounting, run a bounded R44-authorized cohort, inspect real artifacts and attested counts, and apply the rolling cost stop; (6) continue with the next highest-impact eligible blocker while unrelated work proceeds. This is not a requirement to implement the whole target design, a new snapshot system or a new audit platform before producing candidates. Every failure feeds the existing backlog with evidence and an owner. A rollback switches the faulty code path or halts new promotion; it does not erase seals, old failures, provider charges or audit records.

**Tradeoffs and limits:** content-bound audits and independent source probes add latency, storage and some model/audit expense; they prevent a different candidate inheriting trust and enable targeted reuse, but cannot establish an absolute absence of false claims. Snapshots improve replay at the cost of retained artifacts and observation expiry management; publication still needs fresh checks. A strict UNKNOWN state can reduce throughput until facts/probes improve, but labeling missing evidence as false or true creates worse errors; inherited unknown material follows the separate preservation policy. More deterministic composition reduces variability but may inherit upstream defects and cannot substitute for quality evaluation. Conservative HEAD freshness may hold harmless changes until consumed-scope analysis proves irrelevance. A six-product pilot and 53 sealed regressions do not prove the long tail, all ecosystems, production concurrency or the requested 85% yield; expand only on measured real results. A system whose failures remain unresolved should stop with a reproducible diagnosis, not silently lower standards or spin paid retries.
