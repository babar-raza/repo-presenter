## Method and assurance labels

Examined GitHub's live source trees, significant code and tests, current/legacy workflows, authoritative and historical records, stored candidates, GitHub Actions run/job/selected log evidence, an externally visible bot PR, and real upstream issues. Major observed conditions below are linked to inspectable sources. Where a claim depends solely on repository narration, it is explicitly *recorded, not independently reproduced*. No secrets were read, no repository was modified, and no external write was initiated.

**Evidence levels:** `CODE` = source inspected; `TEST` = test present or historical test result inspected; `LIVE` = GitHub job, PR or issue observed; `DOCUMENTED` = repository describes behavior but its effect not established; `UNVERIFIED` = inaccessible or no credible evidence. A whole-workflow success means only that the workflow job(s) succeeded; it is not candidate owner approval or upstream publication. Effort estimates are conditional engineering estimates for planning, **not** commitments or estimates for work performed by this assistant.

**Verification limits:** GitHub was reachable through an authenticated connector, but this environment could not clone a repository into its local execution sandbox (DNS unavailable). Consequently there was no new pytest, Docker or adversarial runtime execution. The private `Aspose/aspose.org` reference repository was not accessible to the connector (404). The claimed October 31 skill behavior/line counts come from the existing project's audit, not a fresh independent comparison. Configuration of GitHub branch protection and App private credentials was not accessible. Source sampling covered priority modules and integration paths rather than every line of the approximately 249 source-code files.

## A. Executive verdict

**Right problem, substantially useful core, undelivered product.** The repo solves a real business need: obtain verified facts from managed FOSS repositories; independently produce a respectful, accurate, customer-useful README through two lanes; preserve evidence and content; and safely publish changes/issues through authorized GitHub App effects on an unattended schedule. Its current implementation has meaningful, tested internals, but does not connect generation to verified upstream publication, issue lifecycle, authenticated App writes or autonomous control in the new repository.

**An additional first-principles finding changes the shortest-path recommendation:** The old `repository-presenter` has *already implemented* GitHub App installation-token acquisition in Actions using `actions/create-github-app-token@v2`, separated read/write jobs, a scheduled issue workflow, gated filing/close/update steps, a proposal workflow, candidate-publication workflow, CI and lockfile checks. It was **still running scheduled GitHub Actions on November 3**, despite its frozen source HEAD being October 20. This is not just code to salvage; it is a live operational system whose state, write ownership, schedules, open effects and kill switches require reconciliation. Rebuilding JWT signing in Python is a possible choice, not the proven minimal path. Prefer adapting existing Action-based token minting and thin CLI-to-effect wiring first.

**Current baseline:** 36 registered repositories, Lane L pipeline-good 12, Lane R pipeline-good 10 according to the newest correction card; no owner-review count; no new-system upstream PR; one actual new-system issue filed locally with a human-authenticated token; reviewer calibration `NOT_PASSED`. The state file's top counters still say R 9, L 12, while its more recent card reports R 10. GitHub Actions shows 188 total new-system workflow runs: 28 successes, 160 failures, all `workflow_dispatch`. These are development-run outcomes, not a sample of production success probability. A Nov 3 Lane R-only run genuinely succeeded: [41657452717](https://github.com/babar-raza/repo-presenter/actions/runs/41657452717).

The root README, missing MIT license and cascade-script false-success exit previously reported were repaired in the newer HEAD and should not be relisted as unresolved. See current [README](https://github.com/babar-raza/repo-presenter/blob/main/README.md), [state item 10](https://github.com/babar-raza/repo-presenter/blob/main/project/state.yaml), [source script](https://github.com/babar-raza/repo-presenter/blob/main/scripts/run_cascade.py).

## G. Strengths, weaknesses and salvage priorities

**Highest-value strengths:** shared fact polarity; pinned/read-only clones; seven-ecosystem extractor investment; two genuinely separate lanes; content preservation and disposition tracking; non-authoring reviewer architecture (but not its current calibration); ledger-backed candidate sealing; immutable process/no-op evidence; Git-ref durable transactions; compartmentalized hosted fact-versus-secret jobs; targeted write permissions and approved effects; recovered historical App workflows.

**Most serious weaknesses:** end-to-end publication absent; current reviewer failed calibration; registry modes preclude one required pilot; incomplete issue lifecycle despite old working source; old and new systems concurrently operational; manual-only new Actions; no local Docker proof; cumulative action failures; inconsistent dashboard counts; user-facing README output quality not benchmarked; maintenance overhead in oversized modules; abandoned supervisor controls; no rigorous owner-facing acceptance funnel.

**Immediate salvage order:** (1) production-effect workflow and App-token orchestration from old repo, (2) missing issue lifecycle/funnel/redetection/close-approval components, (3) current repo's source/evidence/lanes/state as-is, (4) deterministic aspose.org checks *after* direct reference verification. **Do not import** old reviewer fold logic or its old accepted seals as authority, and do not port the legacy 4,829-line CLI wholesale when thin adapters will suffice.

**Preferred target architecture:**

`authorized registry -> clean pinned read-only source -> one facts bundle -> Lane L and Lane R (separate outputs) -> deterministic validations + independent calibrated review -> sealed candidate + fresh no-op proof -> publication-eligible queue -> owner approval / allow-list write gate -> GitHub App token minted by hosted Action -> upstream proposal + gated issue lifecycle -> independently observed GitHub effects -> durable outcome dashboard`.

The same pipeline must work in a minimally isolated local Docker exercise. Local proof can use mocks and a separately injected short-lived scoped installation token for an owner-authorized live pilot; this does not by itself require implementing JWT issuance in Python. All prod signing key operations remain within the official hosted Action unless a concrete requirement proves otherwise.

## I. Prioritized corrective plan — finite, dependency-ordered

**Stage 0: reconcile authority, active writers and observation (small-to-medium; high confidence).** Define authoritative G1–G8 outcome gates separately from 10 audit taskcards. Reconcile the still-running old project: schedules, current issues/PRs, approvals, owner of each effect and safe cutover/rollback strategy. Current new repo stays read-only regarding upstream changes until owner authorization. Make the portfolio status reader produce one timestamped, artifact-bound per-lane/effect matrix. **Gate:** one baseline with no contradictory public progress counters, inventory of every active writer and owner-approved cutover protocol.

**Stage 1: reproducible delivery substrate (medium; medium confidence).** Port or adapt legacy CI/lockfile/test checks to the new Python package. Create smallest Docker execution plan that isolates upstream code, supports known toolchains and proves local CLI + both lane paths; maintain hosted two-job secret boundary. Define a scoped, bounded hosted dispatcher; do not enable unattended writes. **Gate:** clean local Docker run and CI from pinned source/deps, an intentionally corrupted facts artifact blocked, and no credential available in the execution container.

**Stage 2: quality acceptance and lane coverage (high; medium confidence).** Fix reviewer calibration without waiving real-defect recall. Add a direct same-source benchmark against aspose.org when accessible; require blind owner review on at least a small representative cross-ecosystem sample and preservation/inherited section falsifiers. Continue real fail-queue sweeps toward >=25 in each lane, with systemic blast-radius checks. **Gate:** calibrated reviewer on independent corpus; two lanes each >=25 current candidates and complete no-op/preservation proofs. Historical seals do not count automatically.

**Stage 3: install-token and publication vertical slice (medium; medium-high mechanism confidence, owner-action dependency).** Prefer porting `.github/workflows/propose.yml` and verified `actions/create-github-app-token@v2` patterns rather than writing new JWT signing code. Provide thin new-project CLI that calls existing `propose/effect.py` under verified registry permit, hash-bound authorization, calibration and live source recheck. First owner-selects/authorizes exact `cells/net` target; then separately owner-selects/authorizes `3d/python` and its dry_run-to-full mode change. Never silently flip global registry modes. **Gate:** one genuine, bot-authored PR on each mandated target with verified author, SHA, branch, content, dedupe/retry and refusal controls.

**Stage 4: issue lifecycle through App (medium; medium confidence).** Selectively adapt old `redetect`, `close_approval`, `lifecycle`, `funnel`, `batch`, `quality` and appropriate tests, minimizing new glue code. Exercise one genuinely new authorized issue and one safe resolution/close scenario when actually resolved (or a clearly isolated test target with explicit approval). An App-authenticated dry run is not a filed issue. **Gate:** discovery -> dedupe -> approval -> App file -> track/assign where authorized -> proof of resolution -> close, each observable externally. No owner approval record may be synthesized by the agent.

**Stage 5: unattended production and retirement (medium; medium confidence).** Run scheduled read-only/shadow mode first, then narrowly authorized effect mode with bounded concurrency, budgets, retry/recovery and alerting; confirm the exact outbound effects. Reconcile pending old issues/PRs and disable superseded schedules by an explicit owner-approved transition, not by inference. Only then migrate to the single desired `repository-presenter` repo on GitHub/GitLab with a separately authorized destructive operation. **Gate:** unattended complete cycle through new stack, status/effect reconciliation, recovery drills, owner-reviewed output, signed release decision and exactly one active write authority.

### Conditional implementation-effort assessment

These are **rough engineering effort bands** for an already-onboarded engineer with the same repository/App access the project historically used; they exclude waiting for owner approvals, unknown model-provider outages, and any discovered upstream defects. They are **not elapsed-time commitments** or promises that the work will succeed in those bands.

| Stage | Conditional effort band | Confidence | Why the uncertainty matters |
|---|---|---|---|
| 0 — authority, active-writer reconciliation and scoreboard | 1–3 engineer-days | Medium | Existing script and audit exist; approval and active legacy schedules need careful inventory |
| 1 — CI/lock/Docker safety validation | 2–6 engineer-days | Low–medium | Prior CI workflow exists, but seven platform toolchains and local isolation need real testing |
| 2 — calibration and portfolio candidates | 5–20+ engineer-days | Low | Model behavior and 13/15 additional successful per-lane repositories dominate uncertainty; access to aspose.org required for real G7 proof |
| 3 — App-token plus two upstream publication pilots | 2–7 engineer-days | Medium | Existing workflows/effects lower code effort; real owner authorization and reviewer calibration are prerequisites |
| 4 — issue lifecycle adaptation and genuine effect proof | 3–8 engineer-days | Medium | Old system contains lifecycle modules, but current schema/state adapters and safe close proof are unverified |
| 5 — unattended deployment, cutover and retirement | 2–7 engineer-days | Low–medium | Existing scheduling helps; dual-writer reconciliation and rollback/security evidence are substantial |

Effort bands may overlap with parallel tasks but cannot be summed into a reliable delivery date. The path to reducing uncertainty is to execute one owner-authorized vertical slice before wider implementation, not to add more planning abstractions.

**Absolute stop conditions:** No new feature work unless tied to G1–G8 and an observed failure; no plan-to-plan restarts; no reimplementation of old App/auth/issue functionality without documented missing behavior; no publishing with `NOT_PASSED` calibration; no global registry flip; no reviewer rejecting evidence silently overridden; no production cutover until the full gate matrix passes. A taskcard closing by a decision to defer must leave its corresponding G-goal `OPEN`, not `DELIVERED`.

## J. Production-readiness verdict and the five decision questions

**Production-ready today?** The core evidence/acquisition and some per-repo lane execution paths can be run and produce reviewable artifacts. The *product* is **not** production-ready: important effect and autonomy paths are disconnected.

**Already autonomous?** Not the new system: its single hosted workflow has only manual dispatch. The legacy system still has autonomous scheduled monitoring and issues analysis, a material existing asset.

**Accepted candidates?** Latest recorded current pipeline-good count is L12, R10, not owner-accepted and not automatically publication-eligible. Strict calibrated/current owner-ready acceptance has not been independently established to the required 25-per-lane threshold.

**Actual working issue/publishing capabilities?** One new-system issue was filed using a local human token; zero new-system upstream PRs. Old system has proven App bot PR creation and scheduled issue workflow execution (but live close/assignment outcomes are not fully established from this audit).

**Minimum remaining work and production blockers?** Calibrate reviewer; preserve/fix lane output quality; recover existing App/issue/proposal shell; connect two external effects; implement local Docker proof and new production scheduler; reconcile active legacy schedules; reach objective acceptance counts and owner review. The shortest credible route is **selective legacy-shell reuse around the stronger new core**, not wholesale rewrite or continuing to build credential/issue infrastructures already present.

**Five questions:**

1. **Are we building the right thing?** Largely yes, but the construction order is wrong: verified core has expanded before user-visible effects.
2. **Have we built it correctly?** Significant internals are correct and verified in specific runs; the complete product is not independently production-proven.
3. **What should have been done differently?** Reuse the old App/effect/issue workflows earlier; separate code/plan progress from observable outputs; freeze and version acceptance; require exact live proof before adding additional layers.
4. **What should be kept, fixed, simplified or discarded?** Keep fact/extractor/lane/state/safety cores; repair calibration/fail-queue/CI; reuse old workflow/lifecycle; simplify dead governance, large modules and overlapping publication nomenclature; avoid writing bespoke App JWT minting without necessity.
5. **How do we finish?** Define unwaivable G1–G8 acceptance gates, implement dependency-ordered controlled E2Es, prove at least 25 good candidates in **each** lane, publish against mandatory owner-authorized targets, verify issues and unattended operation, reconcile old writers and stop development at a signed production gate.
