## 2. Ranked root causes (class level)

1. **Hard per-unit checks with no terminal fallback turn a style or granular defect into a halted cell (confirmed).** 6 never-sealed cells (Cells C++, Font, PDF Py, PDF .NET, PDF C++, Words Java) die as `OutputRejectedError` after 2-3 asks. Evidence: `authoring.py` ~2285-2300 (`value_tokens`/NO_VALUES_RULE appends a hard error per unit; rejected texts like "spells '1','7'" / "'8','2003'" are product-name numbers or counts), `authoring.py` enterprise-edition rule, `jobs.py:804` (third narrowed ask, then raise). A fallback already exists for one class (`api_row_fallback_slots`, R43(4)). Property: robust, universal. The check is applied the same way to every cell, but the probability that a model keeps some number out of N units grows with N, so it fails the large cells first.
2. **Maintainer-text preservation is a per-unit disposition negotiation whose failures scale with README length and are not terminal-safe (confirmed).** Class BC-17/BC-05 inherited_unit, BC-08, live_readme_loss, disposition_coverage: 12 cells. 11-13 audit already showed rules that cannot all be satisfied (KEPT_EXAMPLE_BLOCK_UNPRINTABLE; "SUPERSEDE_REDUNDANT but not stated"; repair refused by the changes ledger: noop 14, ledger 14, supersede-target 9 of 54 unrepairables). Current examples: PDF Java BC-05/17 on `<version>26.6.0</version>` code block and a 10-piece table; Slides/TeX BC-17 `technical_content`. Property: universal, repeatable.
3. **Register/BC-18 check is per-cell data that grows after the fact, so a seal that passed can fail later (confirmed).** 6 of the 8 failing seals fail only BC-18 (3D .NET, Cells C++, Cells TS, HTML, Words .NET; Cells .NET also BC-14). The false claim is in kept maintainer text or authored prose in 4 of 6 (`origin_kind`: inherited_unit for 3D .NET/Words/Cells TS; authored for Cells C++). 138 OPEN rows with only 2 resolved: nothing in the loop turns a register row into an automatic correction/omission of the matching sentence before seal. Property: reliable, repeatable (a certified seal can flip with no code change). Small certified cells have few rows (median 5) and their candidates avoid them by chance.
4. **Whack-a-mole from a moving code/check base (confirmed, quantified above).** 8 code hashes in 4 days, 36% new-class rate, and 11-13 audit: 7 of 10 new classes came from checks landing between runs. Not a cell attribute, a process property: no pass was run under frozen code on all 40, so universality is untested rather than disproved. Property: reliable, repeatable, proven-on-hosted.
5. **Authored-claim kind/format checks (BC-14, BC-04, claim_contradiction) over large API surfaces (probable).** 7 cells, mostly Cells TS, 3D Py, Cells .NET (Color/FillPattern called a class/property), 3D Py (Entity derived from Mesh). Hits where the model writes a general sentence about types; counts grow with public symbol count. Counter-evidence: Cells Java (2720 symbols) certified, so size is a risk, not a cause.
6. **LLM factuality on authored text (probable, 3 cells: BarCode, PSD Py, OMR)** and reviewer-contract failure on HTML (1, `no_valid_independent_review`: finding cites no product fact). The reviewer contract rejecting a reviewer reply is a JobError with no accepted degraded path.
7. **Upstream-caused (confirmed, small):** GIS (package absent from NuGet, BC-02), PSD Java (terminal), stub `.dae/.fbx` formats in 3D Python/Java, false claims in maintainers' own docstrings and README (3D .NET, Words .NET, Cells C++). Only about 5 of 40 cells have an upstream-caused class (pareto), and every one of those also has pipeline-side failures: R42 says handle by omit/state-unverified, which the pipeline does not do automatically.

## 4. What I could not determine

* **Source size and API surface of the 20 never-sealed cells.** They have no bundle; upstream repos are not reachable via `gh api` or clone from this container (proxy), and I did not run `present --stage facts` for 20 repos. Hence columns facts/public_symbols/units are empty for them in the CSV; the "size predicts failure" finding rests on 19 sealed cells only and is confounded with family and with which cells were audited.
* **Whether failure sets per cell are stable under frozen code**: history is only since 2026-11-14 and spans 8 code hashes; I cannot say "N% of cells would seal in one pass". Any such number would be a guess.
* Per-class counts above are from the latest record per cell (28 cells); 5 cells' last record may predate several code changes (3 days gap). The 6 cohort runs started 11:06Z 11-18 are partly in `latest`.
* `recertify` regenerations column (0-7) hints that deterministic re-rendering is already doing real work; I did not diff what it changed.
* Cause attribution (pipeline vs upstream) for non-certified cells is by class, not by reading each source; treat "pipeline" as the default per R42, with the 6 flagged exceptions in the CSV.
