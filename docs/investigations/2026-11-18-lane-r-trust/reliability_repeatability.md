# R46 lens: reliability and repeatability (read-only; zero provider calls; read 2026-11-18, origin/main c62045c)

Data saved beside this file: present_runs.json (400 `present` workflow runs), present_rows.json (152 epoch-2 runs parsed from hosted logs), laneR_run_signatures.json, ledger.json (read_ledger origin), r_seals.json (Lane R seal-commit facts hashes). Logs: `gh run view ID --log` for all 152 runs since 2026-11-13.

## 1. What I measured

**Run outcomes (present workflow, runs created since 2026-11-13, 152 runs).** 31 success, 115 failure, 6 cancelled. Of the 31 successes, 16 are scheduled unauthorized no-ops (facts job only, e.g. run 43381366046), 15 are real lane runs that ended ACCEPTED. So real lane-run success is 15 of 136, about 11%. Source: `gh run list --workflow present`, jobs API, parsed log line `present: REPO lane X exit N, durable state S`.

**Where the 115 failures fail.** Every one fails at the step `Present (Lane R)` (101), `Present (Lane L)` (6) or both (8). The `facts`, `chain`, restore, cache-save, artifact-upload and ledger steps never fail in epoch 2. No log contains rate limit, HTTP 403, ReadTimeout, ConnectionError, runner shutdown, lost communication or disk-full text (grep over 152 logs; bare "429"/"503" greps are timestamp noise). I could not read run artifacts or `gh cache list` (proxy), so cache evictions are unmeasured.

**Failure split (Lane-step failures, first `failure (class):` line per log).** validation_failed 95: independent reviewer REJECT 51 (claim_contradiction 23, F01 unsupported/contradiction 14, live_readme_loss 5, disposition_coverage 5, duplicate_paragraph 3), deterministic blocking checks with no LLM review made 38 (BC-18 10, BC-05 6, BC-05+BC-17 5, BC-02 4, others). transient 19 (OutputRejectedError: section_authoring output rejected three times after bounded re-asks). Cancelled 6.

**Infrastructure vs pipeline.** Confirmed infrastructure-type: 5 runs cancelled at the job's `timeout-minutes: 90` (present.yml:347), all PDF cells (Java 43548316168; Python 43622625741, 43676128805, 43683717607; .NET 43631633406), each with 44 to 62 provider calls and 2.0 to 3.8 M tokens at ledger settle; one more cancelled run (43661467948) has an empty log, cause unknown. Cache restore missed on 15 of 128 runs that tried (`Cache not found`), restored by prefix on 113. Everything else, 109 of the 115 failures, is pipeline output (model/validators), not infrastructure. The workflow itself is not a visible source of failure in epoch 2; the unreliability is pipeline convergence, not runner flakiness.

**Seal rate (ledger epoch 2, settle entries).** 124 hosted Lane R attempts, 10 sealed R (8.1%), 109 failure, 5 cancelled, 10 success. By day: 11-13 2/25, 11-14 5/55, 11-15 3/37, 11-18 0/7. There are 17 main SHAs, 6 of which produced any seal; no SHA ran more than 18 distinct cells (bb43103b: 20 attempts, 18 cells). Median attempt: 22 calls, 492k tokens, 17 min wall; 8 of 128 settled runs exceeded 60 min. No ledger entries exist between 11-15 and 11-18, so there was no hosted activity in that window. 39 cells attempted, 29 never sealed on hosted, 4 sealed on first attempt, 10 ever sealed. No frozen-code full-portfolio pass has ever run: confirmed.

**Repeatability evidence is thin.** Only 2 (cell, main SHA) groups ever ran Lane R twice or more on the same code, both PDF (Java 9f6f08e8: cancelled then failure; Python bb43103b: cancelled, cancelled, failure). Across 86 consecutive same-cell pairs only 3 were on the same SHA and only 1 of those had the same failure signature. So same-code repeat agreement, the R46 bar's second half, is essentially unmeasured; the existing data is cross-code. What it does show: the signature sequences are mostly stable-by-class, not random. 3D Python fails with REV:claim_contradiction on 8 consecutive attempts across 8 different SHAs; Cells .NET ends BC-05 on the last 4; PDF TypeScript REV:disposition_coverage 3 times running. Others flip between classes (Cells Cpp alternates REV:F01 and BC-02 and OUTPUT_REJECTED; HTML Python BC-07/BC-18 then F01 then OUTPUT_REJECTED), which is a mix of code change and model variation that cannot be separated from this history.

**Preflight on hosted never skips.** 119 `preflight (Lane R)` lines: 49 no prior seal, 68 "consumed input changed", 2 "only mechanism versions changed" (recertify path), 0 `skip=True`. All 68 "changed" lines list `facts` and `environment.toolchains.*` (cargo, gxx, often dotnet; 4 also os/python_version). `facts` is in INPUT_CHANGES (core/preflight.py:65-70), so any facts difference reopens EXTRACTING and new provider calls. Cause of the facts difference is not separable from history: between generated seals of the same cell on the same source revision (11 cells) facts.json hashes differ, but the diffs I sampled (Cells Java, Email .NET, Imaging, Note, Rust) are dominated by added/removed fact families (enum_member, implementation never_thrown/throws, project_file test deps), i.e. extractor code changes, plus `identity:product-knowledge-refresh` (enterprise_target_status, product_homepage_status) which is a live observation. Environment strings differ per run image (python 3.13.15 Windows / .16/.17/.18 Linux across r_seals.json). I did not isolate pure external drift.

**Zero-call determinism checks (mine).**
- `recertify --repository aspose-imaging-foss/Aspose.Imaging-FOSS-for-.NET --lane R --json`, run twice: byte-identical JSON (sha1 5337fa39...), about 26 s each, 0 provider calls. Re-render of the same stored outputs run twice via recertify_history: byte-identical README (sha1 a3939daf). This machine (Linux, py3.13.18) vs the hosted recert chain: three hosted recertifications of that cell at version sets 81a1cb42, 84c5d935 gave the identical README (042e5d1b) and facts; the fourth, at 75b35954, changed it (renderer commit 760e461).
- Confirmed gap: that latest seal (b312760, README 6f549bfb) has sealed_version_set == current_version_set (75b35954...) yet a fresh re-render is a3939daf, a different README (line 208: "These limitations don't apply to [..]" became "See [..]"). Cause: `RENDERER_VERSION = "42"` (renderer.py:134) is a hand-maintained string that feeds the version set (readme/bundle/seal.py:245). renderer.py changed output without a bump in at least 5 commits (d0cbe33, b9e2611, 203b28b, 3236439 under unchanged 39/40/42). So "same version set" does not mean "same bytes", and `recertify` treats such a seal as sealed_by_current and skips writing it.

**Earlier review's claims, verified.**
1. CallStore 12-hex filename: confirmed (jobs.py:178-180); the record stores only job/model/output, no full hash or output checksum (jobs.py:195-198). At 48 bits and a few thousand entries a natural collision is negligible (about 1e-8); not a live cause. Unmeasured, no evidence it fired.
2. Repairs stored under the original key: confirmed (readme/repair/loop.py:_accept, rc.store.put(key,...)); also jobs.py:689/735/779 re-put. Effect: replay of the original request returns the repaired text. This is consistent for replay but means the store holds "final accepted" not "model reply". Whether it fired: repair success lines show it (`repair repaired ...`), harm not shown.
3. Silent fallbacks: present.py:196 `except Exception` in `recertify_instead` prints "not possible ... running the generation pipeline" and regenerates: fired 0 of 152 hosted logs (not silent, it prints). present.py:225 `restore_sealed_bundle` prints "no stored seal restored" 61 files, always "no stored bundle" for never-sealed cells (benign). `readme/reconciliation/inherit.py:47` `except (OSError, ValueError): return REGENERATE` is genuinely silent (no log) but data/aspose_published_readmes.json is present (policy inherit_and_correct, 31 repos) and nothing in logs suggests a miss; unmeasured. Not a demonstrated cause.
4. Related and worse than the above: the repair loop regenerates fresh when the call store lacks the causing section/plan (`the causing section was not in the call store (restored from a sealed bundle); regenerated it fresh`): 10 hosted logs. That is a replay-identity break by construction.

## 2. Ranked root causes (my lens)

1. **No same-code measurement exists, and the hosted loop is built for chasing, not for frozen passes (confirmed).** 17 SHAs in 5 days, 2 same-code repeat groups. Unreliability and unrepeatability cannot be told apart in the data, and each code change resets preflight. Property: proven, repeatable.
2. **Version set under-fingerprints behaviour (confirmed).** Hand-bumped RENDERER_VERSION (and likely sibling component versions) mean seals and fresh renders disagree under an equal fingerprint. Property: repeatable.
3. **Cache/store is keyed by repository and restored by prefix, saved on failure (confirmed mechanism, effect probable).** `presenter-state-<slug>-<run_id>` with restore-keys prefix (present.yml:377-384, 540-546), `if: always()`. A re-run on the same code replays stored accepted outputs; fresh sampling only occurs if request hashes change. Same-code re-runs therefore mostly test replay, not the model, and a stale-code store feeds new code. 15 misses show it is best-effort. Property: repeatable, reliable.
4. **Volatile observations inside "facts" force reopening (probable).** 68/68 sealed-cell preflights reported facts changed; hosted seals can never reach the zero-call no-op. Contributors: live link/product-page status (`identity:product-knowledge-refresh`), toolchain strings, and extractor code changes. Property: repeatable, robust.
5. **Throughput/timeouts on large cells with no progress logging (confirmed for 5 PDF runs).** Present step prints nothing for ~90 min before cancel; settle shows 44-62 calls, so a call-count or token-per-call problem (about 50k tokens/call), not a hang proven. 90-minute cancel discards the in-flight repair state of that attempt (cache is still saved, always()). Property: reliable, universal (PDF cells 0 seals of 27 attempts).
6. **Convergence failures that are deterministic per class, not flaky (confirmed by signature runs).** 3D Python claim_contradiction x8, Cells .NET BC-05 x4. These are fix-class work (other lenses), but for repeatability they show a failure that repeats is a defect, not noise. OUTPUT_REJECTED (19, 'transient') is the only genuinely stochastic class; it is labelled retryable but is the same model-output-rejected class 3 times in a row for Cells Cpp/HTML (hypothesis: prompt/schema mismatch for that cell, not luck).
7. **Silent regenerate fallbacks (hypothesis; not shown to fire).** inherit.py:47; recertify_instead logs but regenerates and thus can burn calls and change a seal's content silently.
